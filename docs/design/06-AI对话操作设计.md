# 06 · AI 对话操作平台设计（Agent 层）

## 核心认知

> 平台是模块化单体，所有能力都在 FastAPI service 层。
> **AI 对话不是一条新链路，只是 service 层的第三个客户端**（前两个：Web UI、API）。

```
        ┌─ Web UI (Vue) ────┐
用户 ───┤                    ├──→ FastAPI service 层(建任务/查询/调度/资产)
        └─ AI 对话 Agent ───┘        │
           (LLM Function Calling,    ▼
            Tools = service 方法)    MySQL / Doris / Airflow / DataX
```

给 AI 包一层 Function Calling，它就能操作平台的一切。
三件事（查询/同步/ETL）是**同一机制**，区别只在**风险等级 → 确认策略**。

## 三类任务的对话流

### ① 数据查询 —— 直接执行，免确认（等价智能问数）

```
用户: 查一下昨天 orders 的下单 Top10 用户
AI:   (生成只读 SQL → 自动加 LIMIT/超时 → 直接执行 → 返回表格+图)
      昨天下单 Top10 如下: [表格/柱状图]
```
只读、有 LIMIT、超时熔断，风险≈零 → 免确认，体验对标 SQLBot。

### ② 数据同步任务 —— 草稿 + 试跑 + 确认上线

```
用户: 把业务库 mysql_sales 的 orders 表每天同步到 Doris 的 ods 库
AI:   已连源库读到 orders 23 个字段。确认三点:
      ① 增量(按 update_time)还是全量覆盖?
      ② 目标表 ods_orders 不存在,按源表自动建(分区 dt)?
      ③ 调度每天凌晨 2:00?
用户: 增量,2点
AI:   ✅ 已生成任务并试跑 100 行成功(1.2s,字段映射无损失)
      [确认上线] 后注册 Airflow,明天 02:00 首跑
用户: 确认上线
AI:   已上线,DAG 已激活 → 任务卡片链接
```

### ③ ETL 任务 —— 同上，多了依赖推荐

```
用户: 基于 ods_orders 做一张 dwd 订单明细,剔除测试账号,每天跑
AI:   SQL 已生成(右侧编辑器可改)。查血缘发现上游 ods_orders 02:00 完成,
      已自动挂依赖,调度建议 02:30。试跑成功: 128万行/8s。[确认创建]
```

## 工具清单（第一版）

| Tool | 干什么 | 风险 | 策略 |
|---|---|---|---|
| `query_data` | 只读即席查询 | 低 | 直接执行 |
| `search_metadata` | 搜表/看字段/查血缘 | 无 | 直接执行 |
| `create_sync_job` | DataX 任务 | 中 | 只产**草稿** + 试跑样本 → 确认 → 上线 |
| `create_etl_job` | SQL 任务 + 依赖 + 调度 | 中 | 同上 |
| `run_job` / `pause` / `rerun` | 调度运维 | 中 | 确认后执行 |
| `publish_api` | 发布数据 API | 中 | 确认后执行 |

## Agent Loop 实现骨架

```python
@app.post("/api/chat")
async def chat(msg: str, user=Depends(current_user)):
    messages = [system_prompt, *await inject_schema_rag(msg), *history(msg)]
    for _ in range(MAX_ROUNDS):
        resp = await llm.chat(messages, tools=TOOLS)
        if resp.tool_calls:                       # AI 想调平台能力
            for tc in resp.tool_calls:
                result = await dispatch(tc, user) # ← 调的是 service 层方法
                messages.append(tool_result(tc, result))
        else:
            return resp                           # 文本 or 任务卡片(待确认)
```

## 五个工程要点（决定能不能用起来）

1. **确认流（HITL）**
   所有 create 类工具只写 `status=draft` 记录，前端渲染任务卡片，用户点"确认"才触发
   DAG 渲染上线——**AI 永远不直接上线任何东西，这条红线不破。**

2. **校验链在工具内部**
   连通测试、字段类型映射、DataX 试跑 100 行（原生支持限制条数）、sqlglot 只读校验、
   EXPLAIN——AI 生成的东西没过校验链不允许出草稿。

3. **元数据是准确率地基**
   对话时把相关表的字段/注释/样例值注入上下文（RAG）；表字段注释规范第一天就抓——
   **AI 建任务的质量上限 = 元数据质量。**

4. **权限走用户身份**
   Agent 以当前登录用户身份调工具，用户没权限的库表 AI 也碰不到——
   代码层鉴权，不是提示词里写"请勿越权"。

5. **实现顺序（先只读后写入）**
   `query_data`(1周) → `create_sync_job`(2周) → `create_etl_job`(2-3周，依赖编排最难)

## 总结一句话

> 平台的每个 service 方法，包一层 JSON Schema 就是 AI 的一个工具；
> 先包只读的，再包写数据的，写数据的全部走草稿 + 确认。
> 做完这一层，平台就是 AI-Native 的数据平台，而不是"带个聊天框的数据平台"。
