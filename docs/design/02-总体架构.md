# 02 · 总体架构

## 架构定稿（全自研版）

```
┌────────────────────────────────────────────────────────────┐
│ 交互层                                                      │
│   Web UI (Vue3)  ──┐                                        │
│   AI 对话 Agent ───┤   两个客户端，同一套 service 层           │
├────────────────────────────────────────────────────────────┤
│ 平台层（全自研，FastAPI 模块化单体）                           │
│   auth   SSO + RBAC（AI 以登录用户身份行事，代码级鉴权）        │
│   meta   元数据 + 资产 + 地图（自研轻量版）                    │
│   integ  数据集成：DataX JSON 渲染 + 校验链 + 执行适配          │
│   sched  数据调度：Airflow REST 封装 + 动态 DAG 渲染器         │
│   dev    数据开发：任务配置 + SQL 工作台后端                    │
│   apigw  数据服务：SQL 模板 → API（详见 05 文档）              │
│   ai     Agent 编排 + NL2SQL + MCP Tools（横切所有模块）      │
├────────────────────────────────────────────────────────────┤
│ 元数据/配置中心（MySQL）—— 一切任务以"配置记录"形式存在         │
├────────────────────────────────────────────────────────────┤
│ 引擎层（不自研）                                              │
│   Doris(OLAP) │ Airflow(调度) │ DataX(同步) │ MySQL(配置)     │
│   部署：单机 Docker Compose 起步；入口 Nginx(静态/TLS/反代)    │
└────────────────────────────────────────────────────────────┘
```

### 三条架构原则

1. **AI 不直接产出执行物** —— 只写配置记录，渲染由平台代码完成（详见 01 文档）
2. **调度用配置驱动的动态 DAG** —— 平台预置 factory DAG 模板，任务实例由配置记录渲染生成；AI 和用户永远不直接写 Python DAG 文件
3. **一切能力在 service 层** —— Web UI 和 AI Agent 是同一层代码的两个客户端，AI 的工具就是包了 JSON Schema 的 service 方法

## AI 建任务三条链路

### 链路 1：数据集成（NL → DataX 任务）

```
用户："把业务库 MySQL 的 order 表每天凌晨2点同步到 Doris 的 ods 库"

① 意图识别 → 判定为"离线集成任务"
② 查元数据：order 表字段/类型（元数据缺失则连源库拉 schema / 反问）
③ 生成结构化配置（非 DataX 原文）：
   { source:  { type:mysql, db:xx, table:order, columns:[...], where:"dt=$bizdate" },
     target:  { type:doris, db:ods, table:ods_order, writeMode:replace },
     schedule:{ cron:"0 0 2 * * ?", dependOn:[] },
     increment:{ strategy:"bizdate分区" } }
④ 校验链：JSON Schema 校验 + 连通性测试 + 字段类型映射检查 + 试读 10 行预览
⑤ 用户对话内确认 → 落库（draft → published）
⑥ DAG 渲染器生成 Airflow Task（调 datax.py 执行渲染后的 JSON）
⑦ 返回任务链接 + 试跑结果
```

**字段类型映射（MySQL varchar → Doris varchar(n) 等）做成知识库表**——这是 AI 生成正确性的关键。

### 链路 2：数据开发 + 调度（NL → Airflow）

Airflow 是 code-first 的，正确姿势是**配置驱动的动态 DAG**：

```python
# 平台预置 factory_dag.py（通用模板），Airflow 扫描配置生成任务实例
# AI / 用户只维护配置记录：
{ workflow_id: "wf_dwd_order",
  nodes: [ { type:"sql",   engine:"doris", sql:"INSERT ...", upstream:["ods_order_sync"] },
           { type:"datax", job_id:123 },
           { type:"python",script_id:45 } ],
  schedule: "0 3 * * *", owner: "..." }
```

AI 生成的 SQL 同样走校验链：sqlglot 语法解析 → 禁止 DDL/DML、禁止全表扫 → EXPLAIN 试跑 → 确认 → 落库。
**跨任务依赖**：AI 基于血缘元数据推荐上游依赖，人工确认。

### 链路 3：智能问数

自研 NL2SQL + RAG（元数据/术语库/few-shot 样例库），问数结果自动出图。
只读、自动加 LIMIT、超时熔断，风险≈零，**免确认直接执行**。
实现细节见 06 文档（`query_data` 工具）。

## 迭代路线

| 阶段 | 内容 |
|---|---|
| MVP | auth + meta 核心表 → integ（一句话建 DataX 任务跑通）→ sched（Airflow 动态 DAG）+ 确认式对话流程 |
| 二期 | dev（SQL 任务编排）+ 智能问数（query_data + search_metadata） |
| 三期 | 资产 + 地图 + 血缘（血缘反哺 AI 推荐依赖，形成正循环） |
| 四期 | apigw 数据服务 + 数据质量（规则引擎：空值/主键/波动） |

> AI 能力的上线顺序与模块顺序交织，单独列出见 04 文档"双维度实施顺序"。
