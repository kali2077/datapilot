## Redis / APISIX 为什么砍掉

结论：**初期都不需要**。模块化单体、内部使用、低 QPS，Redis 要干的每件事都有进程内替代。

| 用途 | 原方案 | 精简替代 | 必须加回 Redis 的时机 |
|---|---|---|---|
| 数据服务限流 | Redis 计数器 | **slowapi** 进程内令牌桶 | apigw 多实例部署（计数器跨进程共享） |
| 查询结果缓存 | Redis + TTL | **cachetools**（TTL+LRU 进程内）；另靠 Doris 自带查询缓存 | 结果集大且复用高 |
| 会话 | Redis session | **JWT 无状态**（短过期+刷新） | 需要服务端强制下线/踢人 |
| 审计/后台任务 | Celery + Redis | 进程内队列批量写 MySQL；定时任务用 APScheduler **或直接做成 Airflow 任务**（调度能力平台本来就有） | — |

| APISIX 职责 | 精简后去哪 |
|---|---|
| 路由/发布 URL | FastAPI Router |
| AK/SK 鉴权 + IP 白名单 | FastAPI Dependency + 中间件（apigw 的 verify_app） |
| 限流/配额 | slowapi 进程内 |

**加回触发条件（一句话规则）：**
- **Redis**：多实例、高并发计数、实时推送（WS pub/sub）三件事出现任何一件。redis-py 加回去是半小时的事
- **APISIX**：数据服务从"内部"变"对外第三方 / 多租户计费级配额 / 需要插件生态（灰度、WAF、计量计费）"。apigw 代码几乎不动，前面套一层即可——因为鉴权/限流/审计本来就在自己手里

> 同理 MinIO 也砍：文件存储初期本地磁盘卷，多实例再换。
> 唯一例外：Airflow 以后上 CeleryExecutor（多机 worker）时，Redis/RabbitMQ 是它的 broker——但那是 Airflow 的依赖，不是平台的。

## 自研边界（一句话）

> **引擎（Doris/Airflow/DataX/MySQL）不自研，平台（FastAPI 那一层）全自研，网关从"独立组件"降级为"你的一个模块"。**

红利：中间层的东西随时可以外面套一层，也可以随时拿掉。

## Monorepo 结构（模块化单体）

```
data-platform/                # 模块化单体起步,不上微服务
├── app/
│   ├── auth/                 # SSO + RBAC（第一天就要有）
│   ├── meta/                 # 元数据 + 资产 + 地图（自研轻量版）
│   ├── integ/                # 数据集成：DataX json 渲染 + 校验链 + 执行适配
│   ├── sched/                # 调度：Airflow REST 封装 + 动态 DAG 渲染器
│   ├── dev/                  # 数据开发：任务配置 + SQL 工作台后端
│   ├── apigw/                # 数据服务（见 05 文档）
│   └── ai/                   # Agent 编排 + NL2SQL + MCP Tools（横切所有模块）
├── web/                      # Vue3
└── deploy/                   # docker-compose 等
```

**为什么模块化单体而不是微服务**：内部产品，微服务只会把运维复杂度提前变现。
所有模块一个 FastAPI 进程 + 独立 module，边界靠目录约束，跑顺了再拆。

**为什么元数据中心也自研**：全栈自研路线下 OpenMetadata 是协议/版本/UI 风格的异物；
Python 栈下 SQLAlchemy inspector 采集 + OpenLineage 收血缘 + 倒排索引搜索，轻量版约两周；
且元数据模型可与 AI 工具链深度耦合——这是自研相对开源套件最大的优势。

## 双维度实施顺序

**模块建设顺序：**

```
① auth + meta 核心表   —— 权限和元数据第一天就要有
② integ 数据集成       —— 一句话建 DataX 任务跑通（MVP 里程碑）
③ sched 调度          —— Airflow 动态 DAG 渲染器
④ dev 数据开发
⑤ apigw 数据服务
⑥ 资产/地图增强        —— 血缘反哺 AI 推荐依赖，形成正循环
```

**AI 能力上线顺序（与模块交织，先只读后写入）：**

```
① query_data + search_metadata —— 约1周，做完即有智能问数（只读免确认）
② create_sync_job             —— 约2周（草稿 + 试跑 + 确认）
③ create_etl_job              —— 2-3周（依赖编排最难）
④ run/pause/rerun、publish_api
```

## 避坑清单

1. **生产调度必须保留人工确认（HITL）**——AI 生成 ≠ 直接上线
2. **元数据质量决定 AI 准确率**——表/字段注释规范开工第一天就抓
3. **权限在代码层做租户/角色隔离**——AI 以用户身份行事，不靠提示词约束
4. **别微服务起步**；**别开源件堆砌**（AllData 教训）
5. **二开源码 = 接盘维护**——平台全自研后此条风险归零，但引擎选型升级（如 Airflow 大版本）要纳入规划
